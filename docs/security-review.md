# Security review

## 2026-11-04 PostgreSQL persistence (v0.9.0, Stage A)

Production structured data, identity/permission checks, administrator configuration and attachment metadata move to PostgreSQL. Related writes use one checked-out connection and transaction under a shared advisory write lock; nested failures poison the outer transaction. Authentication throttles, password-verification leases and scheduled-backup ownership are database-backed. Startup validates initialized data, schema version and the actual configured non-owner login, rejects elevated roles/memberships and fails closed on storage failure. Production has no writable JSON fallback. Existing product delegation remains unchanged; named-family activation is a separate release.

The runtime requires narrow DML plus read-only schema-version access, with no schema creation, truncation, ownership or elevated memberships. Offline DDL credentials must never enter the routine app container. Provisioning must examine effective `PUBLIC` grants on the shared service; runtime startup cannot prove isolation from every other application's grants. Stop if isolation requires changing another application's permissions. Pool/timeouts bound shared-server pressure. URLs cannot override the target, role or resource settings; remote TLS must verify the server. SQL values remain parameterized; CI identifiers come from fixed scratch-name/table allowlists.

Offline dry-run/import/verify preserve account IDs/password hashes, issuer bindings, permissions, event alignment, replay tombstones and fractional ledger values. Imports require an empty target, with identical manifest replay limited to verification. Fresh installations use explicit offline `init`; runtime never bootstraps an administrator. Private manifests contain personal identifiers/totals and must be protected. Snapshot capture checks hashes and safe regular paths, rejects symlinks and bounds assets at 512 MiB. Database snapshots, assets and manifests are captured consistently; archives omit the external `AUTH_SECRET`, which must be recovered separately to decrypt OIDC/SMTP values. A current verified reverse export is required for rollback after database writes.

CI runs real PostgreSQL 17.11 in an isolated loopback service with generated credentials, separate administrator/runtime identities and independent databases/processes for repository, migration/restore, auth, actions and protected-media tests. The media fixture applies dormant family SQL only to its scratch database. These are automated regression checks, not production provisioning, live OIDC, shared-server grant review or end-to-end deployment evidence. See [database operations](database.md) for acceptance and recovery steps. This documentation/CI change adds no interactive controls; it does not establish a new whole-app accessibility conformance result. Existing manual/automated UI evidence below remains scoped to the screens and versions recorded.

A fresh local Linux Docker rehearsal of the proposed runner configuration passed 52 tests and 229 assertions using Node 22.23.4, npm 10.9.9, Bun 1.4.4 and PostgreSQL 17.11. It included initialization rollback/concurrency, account overwrite rejection, migration/recovery, runtime privilege rejection, administrator authorization races, evidence/avatar registration and media authorization. Clean installation first exposed a missing nested lockfile entry; after repair, `npm ci` and the complete runner passed. The temporary proof service had no host port and was removed afterwards; existing local fixtures and production services were untouched. This records local runner proof, not a GitHub-hosted workflow result.

The isolated staged production build passed 336 ordinary tests, with 48 database-gated cases skipped and covered separately by the restricted-role suite, plus lint, type checking and build. Browser checks exercised local sign-in, habit creation/completion/undo, wallet changes, limited reward redemption followed by immediate editing, and persisted state after restart. Affected dashboard, wishlist and coin screens passed final axe WCAG checks; mobile views and 200% CSS zoom had no horizontal overflow. Notification focus guards remain an automated warning: manual Tab/Shift-Tab checks verified immediate focus handoff without leaving focus hidden. This is scoped accessibility evidence, not whole-app conformance. The four existing React hook lint warnings remain.

The dated sections below describe earlier JSON releases. Their process-local/crash-consistency limitations are historical for migrated production storage; development/test/demo legacy JSON still retains those limits. Remaining operational concerns include targeted public-login lockout, trusted administrator-controlled OIDC discovery/SMTP endpoints, host asset/backup permissions, secret recovery, orphan cleanup after committed metadata removal and the backup memory ceiling. Database transactions do not prove real-world habit completion or fully validated multi-replica deployment.

## 2026-11-04 scheduling, any-time actions and family oversight (v0.8.0)

Family reads and redemptions reload the acting account and manager scope from one current authentication snapshot. Managers can act only for assigned members; selecting themselves still requires their ordinary edit or redemption permissions. Any-time completions validate the single beneficiary and creator-selected recorder policy on the server. Serialized requests use UUID replay protection, and undo retains a voided record so retrying the original request cannot restore its reward. Evidence on withdrawn records is inaccessible even if file deletion fails. Approval credits the recorded beneficiary rather than the acting manager.

Schedule inputs have bounded intervals, occurrence counts and canonical dates. Calendar evaluation preserves anchored intervals and uses bounded date windows. Unsafe legacy rules fail closed during evaluation while unchanged schedules can be retained during unrelated edits. Schedule modes cannot change after history exists, and pending approval locks the relevant schedule and assignees. Family reward limits and debits share the existing serialized write and rollback path; the single-process and multi-file crash-consistency limits below remain.

Regression tests cover current/revoked manager scope, unrelated-account isolation, forged beneficiaries, recording policies, retry/concurrency protection, undo, approval, reward limits and write rollback. An isolated production build exercised admin, manager, member and unrelated accounts with synthetic data: 20 workflow checks and 21 responsive axe scans at 1440, 390 and 320 pixels passed, with no overflow, reported WCAG violations, page errors or missing translations. These checks do not establish full-app accessibility conformance or real-world completion accuracy. No dependency was added.

## 2026-11-02 dashboard layout and OIDC button name (v0.7.0)

The OIDC sign-in button name is stored separately from provider credentials. Only an administrator can change it; input is limited to 64 plain-text characters, and React renders it as text. Renaming does not change the active issuer, callback, client secret, or linked accounts and does not require a container restart. The dashboard and compact-row changes affect layout only; they do not change completion or coin authorization. Dashboard sections retain their document order and keyboard reorder controls in the fluid column layout.

An axe WCAG 2.2 AA check of the local Admin panel and dashboard reported no violations. The habit list check found an unnamed action menu and low-contrast reorder help; both were corrected. Recheck the final build after deployment for browser- and data-specific differences.

## 2026-11-02 selected improvements (v0.6.0)

Approval and reward decisions run in serialized server actions. New item creators are assigned server-side, approval settings require the creator or an administrator, and approver IDs must name existing accounts. A pending submission does not award coins. A designated approver may approve their own submission by product choice. Rejected records do not count as completions and can be resubmitted. Reward values for pending submissions are captured at submission time, including any active boost. Legacy items have no creator identity; only administrators can change their approval settings.

Evidence is limited to 2 MB JPEG, PNG, or WebP input. Sharp decodes and re-encodes it as WebP with a 20 megapixel input cap and without metadata. Files are owner-only; a protected route permits only the completer, item creator, and designated approvers, and sets private no-store, nosniff, and a sandbox content security policy. Withdrawing a completion or deleting its item removes the evidence file after the data write. A host crash during that cleanup can leave an orphaned file; it is not served because the record is gone, but an administrator may need to remove it from `data/evidence`.

Approval review returns the updated item only to an assigned member or administrator. A designated approver outside the item receives the decision and their own visible coin ledger, preventing the review action from exposing the item's description, drawing, other participants, or completion history. The v0.6.0 Codex Security diff scan `f6e66df6-4c5e-4f55-95ab-268b15a20e3d` found this one low-severity disclosure in the working-tree snapshot; it was corrected before release.

An approval award stores the daily target at award time. If undoing a later approved check-in drops that day's count below the same target, the earlier award is reversed and can be earned again; awards issued before a target edit remain intact. When a named approver is deleted, a remaining creator becomes the fallback approver, or a remaining administrator if the creator is unavailable. Deleting a completing account rejects its pending submissions and removes its evidence references and files. These account-deletion writes still share the existing JSON multi-file crash-consistency limit.

Reminders run only in an open browser tab and use local browser storage to avoid repeat alerts. There is no background push or server-side scheduling. The existing single-process JSON write and crash-consistency limits below still apply to rewards. New UI strings currently use English in non-English locale files pending translation review.

The approval queue and task approval form were checked with axe against WCAG 2 A/AA, 2.1 AA, and 2.2 AA. A low-contrast description, a stale approver-search `aria-controls` reference, and an unsupported label on a paragraph were corrected. Closed Radix emoji/date popovers produce inconclusive `aria-controls` checks; short coin-count and chart labels remain inconclusive automated contrast checks that need manual review.

## 2026-11-02 scheduling and organization update (v0.4.0)

The task date picker writes an ISO day in the configured timezone. Every-other-day recurrence rules include a saved start day and are limited to 365-day intervals without additional filters; server validation rejects unanchored or malformed rules. Manual ordering uses a dedicated serialized server action that requires habit write permission, checks the exact set of visible active items, bounds IDs and list size, and reloads the latest data before changing positions. This prevents a reorder from overwriting a concurrent habit edit. Positions on shared items are visible to all assigned members. Compact and combined-view preferences remain in browser storage. No new dependency or external endpoint was added.

The local demo was used to save and reopen a calendar-selected task date, move habits and confirm order persistence after reload, view compact cards, and show both tasks and habits in the combined Today list. Axe reported no WCAG 2 A/AA, 2.1 AA, or 2.2 AA violations on the checked dashboard, compact list, schedule dialog, and open task calendar after mobile-nav contrast, emoji-button name, and dialog-description fixes. Axe could not automatically resolve chart-label contrast and some Radix popover focus/ARIA references; these need manual review and do not establish full-app WCAG conformance. The existing four React hook lint warnings remain. Codex Security diff scan `e90035ce-f4c3-4a90-905d-f8bbeb6af9a7` reviewed all 25 changed source files and found no new security findings. That static scan did not test the live instance or OIDC provider.

## 2026-11-02 shared reward policy correction (v0.3.1)

Future shared-habit completions credit only the member who records the target-reaching completion. Existing coin transactions are not rewritten. Undo still reads each completion's recorded recipients, so older awards to multiple members reverse against the original accounts. Focused regression tests cover recorder-only credits, ownership, target changes, concurrent submissions, and reversal of an older group award. The reward path remains serialized within one process and retains the separate-file crash-consistency risk described below. This change adds no UI controls; the earlier accessibility findings remain applicable.

## Validation

- Shared completion regression tests cover recorder-only rewards, one award per local day after target edits, recorder-only member undo, administrator recovery, stale administrator saves, direct-write bypasses, legacy records, membership and reward-setting changes, the 20,000-event limit, concurrent submissions, zero-value rewards, and rollback after an ordinary coin-file write failure. The UI hides or disables undo when the signed-in member did not record the latest completion. The icon-only mobile Undo button now has an accessible name. Pa11y was not available in the offline package cache, so these UI changes have not had a new automated WCAG run.
- The Admin panel change was reviewed for authorization, CSRF, provider changes, secret handling, input bounds, log disclosure, and accessible form controls. Its server actions require an administrator session, a current local password for OIDC, and reject demo mode. The OIDC secret is AES-256-GCM encrypted with a key derived from `AUTH_SECRET`, never returned to the browser, and saved in an owner-only file. A new secret is mandatory when the issuer or client ID changes; changing an issuer with linked accounts and disabling OIDC while passwordless linked accounts remain are blocked. A damaged saved configuration disables OIDC at startup instead of restoring the environment provider. The active provider remains fixed until restart, while the log threshold changes immediately.
- Generic OIDC uses an `oidc` callback and standard discovery. Existing Authentik environment configuration keeps its `authentik` callback until an administrator opts into the generic setup. New links save the provider issuer with the subject; old links are accepted only for the legacy issuer, which is retained on the first in-app save. Self-linking still requires a matching verified email claim.
- A disposable local administrator signed in, navigated both Settings tabs by keyboard, and saved a log level. The tab panels, labels, focus behavior, headings, and status message were checked in the browser. Axe returned no WCAG 2 A/AA, 2.1 AA, or 2.2 AA violations or incomplete checks on either Settings tab after contrast and touch-target fixes. This does not prove every screen or interaction meets WCAG 2.2 AA.
- Unit and security tests, TypeScript, lint, and production build cover the changed code.
- A local browser check covers local sign-in and the mandatory-email screen. Pa11y/axe found no issues on those screens. On the dashboard, axe marks five SVG chart labels for manual contrast review because it cannot determine the background behind the chart. The rendered labels use the foreground color; this is a tool limitation, not a measured contrast failure.
- A live local account with a mandatory email was linked to the existing Authentik identity after the account owner entered their local password. The saved account record had one matching email and a linked identity. After deploying image `habittrove-fork:7923877`, a fresh Authentik sign-in reached that account's dashboard with its existing habits and coin balance. The Unraid container was healthy and returned HTTP 200 locally, and its saved template points to the deployed image. The prior image and account backup were retained for rollback.
- This live check covers one existing account and one Authentik sign-in. It does not establish behavior for every identity-provider failure or future multi-user migration.

## Remaining risks

- An administrator can configure an OIDC issuer on an internal HTTPS address; Auth.js will contact its discovery endpoint. Restrict administrator access and treat the issuer as trusted infrastructure. Rotating or losing `AUTH_SECRET` makes an in-app saved client secret unreadable; keep a secure backup and restore the original secret or reconfigure OIDC. A malformed admin-config file requires host-side repair or removal while the app is stopped.
- Directly changing a provider issuer through container environment values bypasses the in-app linked-account guard. Keep the issuer stable for linked accounts, or unlink them first. Register `/api/auth/callback/oidc` with the provider before switching from legacy Authentik settings to the generic setup.
- A provider may issue pairwise subjects that change with the client ID. If the client ID changes, linked users may need to sign in locally and relink; keep a working local administrator recovery path.
- The log-level selector filters HabitTrove's server backup, scheduler, and data-action logs only. Auth.js, Next.js, browser logging, and container log retention are managed separately. Error objects may still contain operational details; restrict access to container logs.
- Use one application process per data directory. JSON writes and failed-login throttling are serialized only inside one process; multiple replicas can race or bypass the throttle. A transactional store and shared rate limiter are needed before scaling out.
- Habit completion is self-reported. An authorized member can still enter false past completions, one at a time, and receive rewards. Limiting edits to the past year reduces bulk abuse but cannot prove real-world activity.
- Completion and coin files are separate JSON files. The server serializes writes within one process and rolls back the habit file on a coin write error, but a process or host crash between file renames can leave one file ahead of the other. Restore a consistent backup or reconcile the completion and its transaction IDs before resuming writes. No rewards are backfilled for earlier shared completions. A day with legacy events is conservatively treated as already awarded, even if it was not.
- Files created by previous versions may have broad permissions. Restrict `data` and `backups` on the host before deployment. New files are owner-only.
- The initial email entered for a local account is not verified by email. Automatic Authentik linking requires a current local password and a matching Authentik email claim marked verified by the identity provider.
- Some new security UI strings use English fallback in non-English locales. Complete translations before treating those locales as fully localized.
- The development dependency audit still reports moderate advisories in old lint-tool dependencies. The production dependency audit reports none; a compatible lint-tool upgrade remains to be evaluated.
